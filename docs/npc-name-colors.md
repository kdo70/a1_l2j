# Цветные имена NPC (патч движка)

Имя NPC — белая строка под титулом — рисуется движком, и в Interlude его нельзя
покрасить ни пакетом, ни данными клиента: см. [npc-title-colors.md](npc-title-colors.md),
там разбор того, почему это так, и как красится титул.

Этот документ — про то, как имя всё-таки красится: правкой `engine.dll`.

Инструмент — [tools/client/patch_engine_npc_name_color.ps1](../tools/client/patch_engine_npc_name_color.ps1).
Общий контекст модификации клиента — [enchant-and-client-modding.md](enchant-and-client-modding.md),
пример такой же бинарной правки — [enchant-on-icon.md](enchant-on-icon.md).

---

## 1. Что сделано

Два независимых патча. Раздел 4 — про первый, привязывающий цвет к id NPC в
клиентском файле; раздел 7 — про второй, которым цветом обеих строк управляет
сервер из `data/xml/npcs`. Дальше по порядку.

Первый — патч из 61 байта: **один байт на месте** и 60 байт кода в
0xCC-паддинге сразу за функцией. После него имя NPC берёт тот же цвет, что и его
титул, — то есть цвет из `npcname-e.dat`, которым уже управляет
[npc_title_colors.txt](../tools/client/npc_title_colors.txt).

Ничего, кроме перекрашенных вручную NPC, не меняется: три цвета, которые
использует стоковый файл, и цвет титула, который aCis шлёт игроку, объявлены
нейтральными и уходят на прежнюю ветку.

---

## 2. Движок это уже умеет

`engine.dll` собран **с полной таблицей экспорта MSVC — 10 083 mangled-имени**.
Функции ищутся по имени, гадать не приходится. Экспорт — переходник
`e9 rel32` из таблицы инкрементальной линковки, настоящее тело за ним.
`ImageBase` — `0x10300000`, RVA = смещение в файле + `0xC00`, `.code` имеет
характеристики `0xE0000020`, то есть уже исполняемая и записываемая.

`?GetNameColor@User@@QAEK_N@Z` (RVA `0x181760`, 208 байт) целиком:

```
karma = this->[0x198]                       ; GetCriminalRate возвращает это же
clamp(karma, 0, 0xFF), с добавкой karma/16+100
color = AA=FF, RR=FF, GG=FF-karma, BB=FF-karma
if (karma > 0)              return color    ; белый → красный
if (this->[0x194] == 1)     return 0xFFFF00FF   ; GetGuiltyStatus, флаг → фиолетовый
unique = this->[0x308]                      ; GetUniqueNameColor возвращает это же
if (unique != -1)           return unique   ; ← произвольный AARRGGBB, отдаётся как есть
d = (short)this->[0x2E2]                    ; разница уровней
if (0 < d <= 0xFF)          color = градиент по d   ; отсюда голубоватые имена высоких мобов
tail:
if (this->[0x194] == 2 && arg) color = 0xFFFF00FF
return color
```

**То есть произвольный цвет имени в движке уже есть** — просто у NPC в `[0x308]`
всегда `-1`. Игрокам туда кладут цвет из `CharInfo` / `UserInfo`
(`writeD(getAppearance().getNameColor())`); в NPC-пакете такого поля нет.

Формат — `AARRGGBB`: это видно и по фиолетовой константе `0xFFFF00FF`, и по
формуле кармы.

Разложение полей `User`, которое понадобилось по дороге (каждое подтверждено
одноимённым экспортом-геттером вида `mov eax,[ecx+X]; ret`):

| смещение | что | геттер |
|---|---|---|
| `0x190` | цвет титула | `GetNickColor` |
| `0x194` | guilty status (1 — флаг, 2 — ещё что-то) | `GetGuiltyStatus` |
| `0x198` | карма | `GetCriminalRate` |
| `0x2E2` | разница уровней, `short` | — |
| `0x304/0x308/0x30C` | «уникальные» цвета, пишутся сеттером RVA `0x42710` | `GetUniqueNameColor` (`0x308`) |

---

## 3. Почему цвет берётся из `[0x190]`

Потому что это тот же цвет, которым рисуется титул, и он лежит в самом объекте,
а не тянется из таблицы при отрисовке. Проверено так: у `GetNameColor` ровно три
места вызова, все в одной функции (RVA `0x35D620`, `0x35D68A`, `0x35D6C4`) — это
и есть отрисовка надписи над головой. И прямо перед первым из них:

```
35D5D6  8b be 90 01 00 00   mov edi,[esi+190h]     ; esi = User*, edi = цвет титула
...
35D61C  51                  push ecx               ; аргумент-bool
35D61D  8b ce               mov ecx,esi
35D61F  e8 ...              call User::GetNameColor
35D624  89 45 70            mov [ebp+70h],eax      ; цвет имени
35D62A  e8 ...              call ...
35D62F  57                  push edi               ; цвет титула — в отрисовку
```

Одна функция, один объект, два цвета. У `GetNickColor` при этом **ноль** мест
вызова по всему dll — цвет читают инлайном, как здесь.

## 4. Сам патч

### Точка врезки

```
180BCF  8b 91 08 03 00 00   mov edx,[ecx+308h]     ; unique
180BD5  83 fa ff            cmp edx,-1
180BD8  74 04               je   180BDE            ; ← единственный изменённый байт
180BDA  8b c2               mov eax,edx
180BDC  eb 3e               jmp  180C1C
180BDE  ...                 ; градиент по разнице уровней
180C1C  83 fe 02            ; общий хвост
180C30                      ; конец функции, дальше 63 байта 0xCC
```

Меняется операнд `je`: `04` → `57`, и «уникального цвета нет» ведёт теперь в
кейв (`180BDA + 0x57 = 180C31`). Всё остальное на месте байт в байт.

### Кейв

```
180C31  mov edx,[ecx+190h]        ; цвет титула
180C37  test edx,edx
180C39  je   L                    ; 0 — это не цвет, а неинициализированное поле
180C3B  or   edx,FF000000h        ; альфу навязываем сами, какой бы её ни оставил загрузчик
180C41  cmp  edx,FFA9E89Ch
180C47  je   L                    ; бледно-зелёный — стоковый цвет титула
180C49  cmp  edx,FFFE8B3Fh
180C4F  je   L                    ; оранжевый Raid Boss / Raid Fighter
180C51  cmp  edx,FFFF8000h
180C57  je   L                    ; оранжевый Quest Monster
180C59  cmp  edx,FFFFFF77h
180C5F  je   L                    ; Appearance._titleColor, дефолт aCis для игрока
180C61  mov  eax,edx
180C63  jmp  180C1C               ; в хвост — карма и флаг уже отработали выше
180C68  L: jmp 180BDE             ; в стоковую ветку
```

60 байт из 63. Пятый нейтральный цвет уже не влезет — скрипт это проверяет и
отказывается собираться.

Три вещи, которые делают этот патч сильно проще, чем
[правку `nwindow.dll`](enchant-on-icon.md):

- **Ни одного абсолютного адреса.** Только чтения по `ecx`, непосредственные
  значения и относительные переходы — значит, `.reloc` трогать не надо, и
  переезд модуля патчу безразличен.
- **Кейв внутри `.code`**, внутри её `VirtualSize`, а секция и так исполняемая —
  ни флагов, ни размеров секций менять не надо.
- **`ecx` и `eax` сохраняются.** `ecx` нужен ветке с градиентом, `eax` держит
  цвет, посчитанный по карме, и переписывается только на той ветке, которая
  реально подменяет цвет. Поэтому возврат в стоковый код ничего не ломает.

### Нейтральные цвета

Подменять цвет всегда нельзя: тогда **все** мобы получили бы бледно-зелёные
имена, а рейд-боссы — оранжевые. Поэтому цвет титула, совпавший с одним из
стоковых, уходит на прежнюю ветку.

`FFFF77` в списке — страховка со стороны игроков. Игрок сюда попасть не должен:
у него `[0x308]` заполнен из `CharInfo`/`UserInfo`. Но проверить, не превращает
ли клиент белый `0xFFFFFF` в `0xFFFFFFFF` (то есть ровно в `-1`, «цвета нет»),
не запуская игру, нельзя, а если превращает — игрок с дефолтными цветами дошёл
бы до этой ветки и получил бы имя цвета своего титула. `FFFF77` — это и есть
дефолтный `Appearance._titleColor` в aCis, так что такой игрок всё равно уйдёт
на стоковую ветку.

Список задаётся ключом `-NeutralColors`.

## 5. Применение

Цвета задаются один раз, в [npc_title_colors.txt](../tools/client/npc_title_colors.txt),
и красят обе строки — имя и титул:

```
powershell -ExecutionPolicy Bypass -File tools\client\npc_title_colors.ps1 ^
    -ClientSystemDir "<клиент>\system"
powershell -ExecutionPolicy Bypass -File tools\client\patch_engine_npc_name_color.ps1 ^
    -In "<клиент>\system\engine.dll"
```

Первый скрипт перебирает `npcname-e.dat`, второй — правит движок; второй нужен
один раз, первый — после каждой правки таблицы цветов.

Патч кладёт рядом `engine.dll.prenpcname.bak` и **отказывается работать**, если
хвост `GetNameColor` не совпал байт в байт с ожидаемым или паддинг за функцией
не свободен. То есть на чужой сборке клиента и на уже пропатченном файле он
просто ничего не делает. Чтобы поменять список нейтральных цветов — восстановить
из `.bak` и прогнать снова.

**Раздача.** `engine.dll` — отдельный файл клиента, проверка версии из
[client-version-check.md](client-version-check.md) следит только за
`interface.u`. Патч ничего не ломает на клиенте без него — там просто белые
имена, — но и обязательным сам себя не делает.

## 6. Что сделано на тесте

Гейткиперу **30006 (Roxxy, Глудио)** цвет в `npcname-e.dat` выставлялся в золотой
`FFD700` (стоковое — `A9E89C`).

**Проверено в игре: работает.** Клиент с патченым `engine.dll` запускается,
имя красится.

С появлением серверного цвета (раздел 7) Roxxy переведена на него, а её запись в
`npcname-e.dat` возвращена в сток — чтобы источник цвета был однозначен. Сам
механизм из этого раздела никуда не делся: он остаётся способом привязать цвет к
**id NPC**, не трогая датапак и не пересылая ничего по сети.

Офлайн-проверки, которые к этому вели:

- хвост `GetNameColor` совпал с сигнатурой, 63 байта паддинга за функцией
  свободны;
- собранный код разобран обратно вручную: все четыре `je` и оба `jmp` попадают
  ровно в `180C68`, `180C1C` и `180BDE`;
- за кодом остались `cc cc cc`, следующая функция (`180C70`) не задета.

Не проверено:

- кладёт ли клиент альфу в `[0x190]` и в `[0x308]` (патч написан так, чтобы это
  было неважно, но это рассуждение, а не наблюдение);
- попадает ли на новую ветку что-нибудь, кроме NPC, — саммоны и петы туда
  попадают, но их цвет титула стоковый, так что ветка их отпускает.

## 7. Цвет с сервера, на каждый инстанс

Второй патч — [patch_engine_npc_packet_color.ps1](../tools/client/patch_engine_npc_packet_color.ps1) —
кладёт в `UniqueNameColor` цвет, пришедший **с сервера, в пакете `NpcInfo`**.
`GetNameColor` предпочитает его всему, кроме кармы и флага, поэтому серверный
цвет перебивает цвет из `npcname-e.dat`, а NPC, про которого сервер молчит,
остаётся на первом патче. Патчи независимы, каждый работает сам по себе.

### Как клиент разбирает пакеты

Не вручную. Сетевой слой (`UNetworkHandler`) разбирает пакет **по строке
формата**: `parse(reader, ptr, "формат", &поле1, &поле2, ...)`, где `d` — dword,
`c` — байт, `f` — float, `S` — строка (два аргумента: буфер и его размер).
Функция возвращает продвинутый указатель, поэтому вызовы сцепляются.

Обработчик `NpcInfo` — **RVA `0x13A470`** (file `0x139870`), и он разбирает
пакет ровно двумя вызовами:

| строка формата | VA | поля |
|---|---|---|
| `ddddddddddddddddddffffdddcccccSSddd` | `0x1088B5BC` | от `objectId` до трёх нулей после титула |
| `dddddccffdd` | `0x1088B5AC` | `abnormalEffect`, кланы и гербы, `moveType`, `team`, коллизии, `enchantEffect`, `isFlying` |

Обе совпадают с `AbstractNpcInfo.NpcInfo.writeImpl()` поле в поле — это и есть
подтверждение, что найден именно тот обработчик.

**Главное свойство разборщика: каждое поле проверяется на конец пакета**
(`[reader+0x4EF8]`), и если данные кончились — в приёмник пишется ноль, а
указатель не двигается. Отсюда два следствия: лишние байты в хвосте пакета
стоковый клиент просто не читает, а патченый клиент против сервера без правки
не ломается.

### Транспорт

Сервер дописывает в самый конец `NpcInfo` **один dword `0xC0RRGGBB`** — и только
тем NPC, у которых цвет задан. Тег `0xC0` в старшем байте нужен, чтобы отличить
цвет от последнего dword нетронутого пакета: там лежит `isFlying`, то есть 0 или
1, и старший байт у него нулевой.

Клиент читает эти четыре байта **от курсора, который возвращает разборщик**:
курсор указывает ровно на первый неразобранный байт, то есть на наш dword.

**Читать от конца пакета — не работает, это проверено в игре.** Первая версия
патча брала `[[[ebp+8]+0x48]+0x4EF8] - 4`, и тег не совпадал никогда: что бы
`[reader+0x4EF8]` ни считало, последним байтом полезной нагрузки оно не
заканчивается. Курсор от этого не зависит, а проверка «осталось ли хотя бы 4
байта» делается тем же `[reader+0x4EF8]` в виде `end - cursor >= 4` — тут
неточность конца безразлична, лишь бы он был не меньше.

### Врезки

Все уезжают в кейв — 928 байт `0xCC` за концом обработчика, с `0x13A710`.

**Первая, сразу за вторым вызовом разборщика** (`0x139A8F`, на месте
`add esp,0D8h`). Здесь курсор ещё в `eax`, а аргументы обоих вызовов ещё на
стеке, так что ридер лежит в `[esp]`:

```
13A710  mov edx,[esp]              ; ридер (первый аргумент вызова)
13A713  mov edx,[edx+4EF8h]        ; конец пакета
13A719  sub edx,eax                ; сколько осталось
13A71B  cmp edx,4
13A71E  jb  13A724                 ; сервер ничего не дописал
13A720  mov eax,[eax]              ; наш dword
13A722  jmp 13A729
13A724  mov eax,-1
13A729  call $+5                   \ position independent:
13A72E  pop  edx                   / edx = 13A72E
13A72F  mov  [edx+4Eh],eax         ; кладём в ячейку внутри кейва
13A735  add  esp,0D8h              ; перенесённая инструкция
13A73B  jmp  139A95
```

**Вторая и третья — где обработчик начинает заполнять `User`.** Таких мест
**два**: у обработчика две почти одинаковые ветки, по одной на каждый способ,
которым он добыл объект, и обе несут одни и те же три инструкции —

| адрес | возврат |
|---|---|
| `0x139B3E` | `0x139B48` |
| `0x13A02F` | `0x13A039` |

Отличить их снаружи нельзя, а **NPC в городе идут по второй**. Первая версия
патча резала только `0x139B3E` и не делала ровно ничего; поймано диагностическим
билдом (см. ниже), а не рассуждением. Обе ветки видно по тому, что каждая своим
кодом пишет `[esi+0x190]` — цвет титула, — и таких записей в обработчике ровно
две: `0x139CC8` и `0x13A1BD`.

Код в обеих врезках одинаков (ниже — первая), различается только адрес возврата.
Три инструкции переносятся, и к ним дописывается разбор тега:

```
13A740  mov [esi+8],edi            ; \
13A743  mov edx,[esp+50h]          ;  } перенесённые инструкции
13A747  mov [esi+0Ch],edx          ; /
13A74A  call $+5
13A74F  pop  eax
13A750  mov  eax,[eax+2Dh]         ; забираем отложенное значение
13A756  mov  edx,eax
13A758  shr  edx,18h
13A75B  cmp  edx,0C0h              ; наш тег?
13A75E  je   13A767
13A760  mov  eax,-1                ; нет — «цвета нет»
13A765  jmp  13A771
13A767  and  eax,00FFFFFFh
13A76C  or   eax,FF000000h
13A771  mov  [esi+308h],eax        ; User::UniqueNameColor
13A777  jmp  139B48
```

112 байт вместе с ячейкой. Значение лежит **внутри самого кейва** и адресуется
через `call/pop`, поэтому абсолютных адресов по-прежнему нет и `.reloc` не
нужен; `.code` записываемая (характеристики `0xE0000020`), так что писать туда
можно. `-1` пишется и в случае «тега нет» — чтобы переиспользованный объект
`User` не унёс цвет предыдущего NPC.

### Четвёртая и пятая — титул

Тот же цвет красит и **титул**, верхнюю строку. Его цвет — `[User+0x190]`,
и обработчик заполняет его из `npcname-e.dat`: значит, чтобы цвет титула
приезжал с сервера, надо переписать это поле после того, как обработчик его
записал.

Записей ровно две, по одной на каждую из тех же двух веток, и обе — один и тот
же шестибайтовый `mov`:

| адрес | возврат |
|---|---|
| `0x139CC8` | `0x139CCE` |
| `0x13A1BD` | `0x13A1C3` |

Шести байт хватает на `jmp rel32` целиком, так что переносить, кроме самой
записи, нечего:

```
13A7BE  mov [esi+190h],edx        ; перенесённая запись — цвет из npcname-e.dat
13A7C4  call $+5
13A7C9  pop  edx
13A7CA  mov  edx,[edx+67h]        ; то же отложенное значение, что и у имени
13A7D0  cmp  edx,0C0000000h
13A7D6  jb   13A7F2               ; тега нет — оставляем клиентский цвет
13A7D8  cmp  edx,0C1000000h
13A7DE  jae  13A7F2
13A7E0  and  edx,00FFFFFFh
13A7E6  or   edx,0FF000000h
13A7EC  mov  [esi+190h],edx       ; серверный цвет поверх клиентского
13A7F2  jmp  139CCE
```

Три вещи, из которых состоит эта врезка:

- **Клиентский цвет пишется первым, серверный — поверх.** Поэтому NPC, про
  которого сервер молчит, остаётся ровно таким, каким был, и весь стоковый файл
  продолжает работать.
- **`eax` здесь живой** — в нём `[ebp+8]`, и следующая же стоковая инструкция
  индексирует по нему. Свободен только `edx`, тот самый, в котором приехал цвет.
  Поэтому тег проверяется диапазоном `[0xC0000000, 0xC1000000)`, а не сдвигом
  копии в сторону, как у имени: копию некуда положить. «Цвета нет», `0xFFFFFFFF`,
  из диапазона выпадает само.
- **Оба `cmp` — форма imm32.** Короткая `83 /7 ib` расширяет операнд со знаком;
  это уже стоило одного захода на проверке тега у имени.

Врезки идут по коду **после** первой (которая откладывает значение) и после
своей `fill` — значение к этому моменту уже лежит в ячейке.

Игроков это не задевает: `NpcInfo` — обработчик только NPC, у персонажей и
саммонов свои пакеты и свои обработчики.

### Серверная половина

| файл | что |
|---|---|
| `model/actor/template/NpcTemplate.java` | свойство `nameColor` (`RRGGBB`), `NO_NAME_COLOR`, разбор с `WARN` на кривом значении |
| `model/actor/Npc.java` | `getNameColor()` / `setNameColor()` — шаблон задаёт начальное значение, скрипт может перекрасить конкретного NPC |
| `network/serverpackets/AbstractNpcInfo.java` | дописывает `0xC0RRGGBB` в конец `NpcInfo`, только когда цвет есть |

В датапаке:

```xml
<npc id="30080" name="Clarissa" title="Gatekeeper" alias="clavier">
    <set name="type" val="Gatekeeper"/>
    <set name="nameColor" val="FF3030"/>
```

Шесть hex-цифр `RRGGBB`, без `#`; какие значения допустимы — раздел 8. **Одно
свойство красит обе строки** — и имя, и титул. Значение
не разобралось — `WARN` в лог и NPC остаётся без цвета. Перекрасить живого NPC:
`npc.setNameColor(0xFF3030)` и следом `npc.broadcastPacket(new NpcInfo(npc, null))`,
иначе цвет доедет только тем, кто увидит NPC заново.

Конфига у этой правки нет: она бездействует, пока хоть у одного NPC не появится
`nameColor`, и стоковому клиенту не мешает.

### Что проверено

- сервер собирается (`ant -f source\aCis_gameserver\build.xml`, 2368 файлов, без
  ошибок);
- собранный кейв разобран обратно вручную: все пять `call/pop` и все смещения к
  ячейке сходятся на ней одной, все ветвления и все `jmp` попадают в свои метки
  и в свои точки возврата — `0x139A95`, `0x139B48`, `0x13A039`, `0x139CCE`,
  `0x13A1C3`;
- пропатченный файл сверен с исходным побайтово: изменились ровно пять точек
  врезки и 292 байта кейва, больше ничего;
- патчер отказывается работать, если не совпала любая из пяти сигнатур или
  паддинг занят.

Проверено в игре по частям, диагностическими билдами (см. ниже): врезка
выполняется, `[User+0x308]` — то самое поле, сервер дописывает свои 4 байта, и
курсор указывает ровно на них — у Clarissa читается `FF3030`, у остальных NPC
хвост пуст. Боевой билд с исправленной проверкой тега в игре ещё не смотрели.

**Врезки в титул (`0x139CC8`, `0x13A1BD`) в игре ещё не смотрели вообще.**
Собраны и разобраны обратно, но заходом не подтверждены. Диагностических ключей
у них нет — если титул не покрасится, а имя покрасится, значит дело в этих двух
врезках, и это уже само по себе ответ.

Первая версия (чтение от конца пакета) проверена в игре и **не работала** —
отсюда переход на курсор, см. выше.

Две мелочи, каждая из которых стоила захода:

- `call $+5` кладёт на стек адрес **следующей инструкции**, то есть самой `pop`, —
  смещение к ячейке считается от неё, а не от конца инструкции, которая её
  использует.
- **`cmp r/m32, imm8` (`83 /7 ib`) расширяет операнд со знаком.** Проверка тега
  `cmp edx,0C0h`, собранная как `83 fa c0`, сравнивает с `0FFFFFFC0h` и не
  совпадает никогда. Нужна форма imm32 — `81 fa c0 00 00 00`. Правило простое:
  любой байт от `80h` и выше в короткой форме — это уже отрицательное число.

### Как это отлаживать без отладчика

У патчера есть ключ `-Diagnose RRGGBB`: NPC, которому сервер цвета не прислал,
красится не в «нет цвета», а в этот цвет. Один заход в игру отвечает сразу на
два вопроса, которые иначе неразличимы:

| что видно | вывод |
|---|---|
| все NPC в этот цвет | врезка выполняется и `User+308h` — правильное поле; значит не сходится тег, то есть чтение или сервер |
| ничего не изменилось | врезка не выполняется вообще, либо `esi` там не `User` |

Ключей три, и вместе они сужают до одной инструкции:

| ключ | что делает | что различает |
|---|---|---|
| `-Diagnose RRGGBB` | этим цветом красится NPC, которому сервер цвета не прислал | выполняется ли врезка и то ли это поле |
| `-DiagnoseEmpty RRGGBB` | этим — тот, у кого в пакете не осталось 4 байт | дописывает ли сервер вообще |
| `-DiagnoseRaw` | тег не проверяется, имя красится **прочитанными байтами** | верен ли курсор — и заодно видно, что именно приехало |

Так и разматывалось. Первый билд не изменил **ничего** — значит в `[User+0x308]`
никто не пишет, и нашлась вторая ветка обработчика. Второй дал **бирюзовый у
всех** — врезка работает, поле верное, тег не сходится. Третий дал **белых у
всех, красную Clarissa и золотую Roxxy** — то есть у обычных NPC хвост пуст
(курсор и конец точные), у Clarissa прочитано ровно `FF3030` (сервер шлёт,
курсор точен), а Roxxy ушла на патч А. Единственное, что осталось между
«прочитано верно» и «не сработало», — сама проверка тега, и там нашлось
знаковое расширение `83 /7 ib`.

Полезное следствие для любой будущей отладки: пока патч из раздела 4 стоит,
**золотая Roxxy сама по себе означает `[User+0x308] == -1`** — ветка с цветом
титула срабатывает только при этом условии.

## 8. Какие цвета поддерживаются

Формат везде один: **`RRGGBB`, шесть hex-цифр, без `#`**. Внутри движка цвет —
`AARRGGBB`; альфу оба патча ставят в `FF` сами, задавать её негде и не нужно.

### С сервера, `nameColor` в `data/xml/npcs`

**Любой из 16 777 216 — для титула.** Тег живёт в старшем байте, который в цвет
не входит, так что зарезервированных значений у титула нет вообще.

**У имени одно исключение — `FFFFFF`.** Врезка навязывает альфу `FF`, и белый
превращается в `0xFFFFFFFF`, то есть ровно в `-1`, «уникального цвета нет».
`GetNameColor` уходит на стоковую ветку, и имя выйдет белым — то есть таким же,
но не потому, что мы так сказали. Отличить это можно только по титулу: он
покрасится. Белое имя проще получить, вообще не задавая `nameColor`.

Ещё две оговорки, и обе про смысл, а не про формат:

- `000000` — это чёрное имя, а не «без цвета». На тёмном фоне оно практически
  не читается. «Без цвета» — это отсутствие свойства `nameColor`.
- Цвет **не всегда побеждает**: карма и флаг проверяются в движке раньше
  (см. разбор `GetNameColor` в разделе 2). Для NPC оба нулевые, так что на
  практике это касается только саммонов и петов.

### Из `npcname-e.dat`, `npc_title_colors.txt`

Тоже любой, **кроме четырёх**, которые патч из раздела 4 считает «цвет никто не
выбирал» и пропускает на стоковую ветку:

| цвет | почему в списке |
|---|---|
| `A9E89C` | бледно-зелёный, стоковый цвет титула у всех NPC |
| `FE8B3F` | оранжевый, титул `Raid Boss` / `Raid Fighter` |
| `FF8000` | оранжевый, титул `Quest Monster` |
| `FFFF77` | `Appearance._titleColor`, дефолтный цвет титула игрока в aCis |

Список меняется ключом `-NeutralColors` у патчера, но убрать оттуда первые три —
значит покрасить имена всем мобам, рейд-боссам или квестовым монстрам сразу.
Если нужен именно один из этих оттенков — берите его с сервера, там ограничений
нет.

### Кто кого перебивает

Имя, сверху вниз, как решает `User::GetNameColor`:

| приоритет | откуда | когда срабатывает |
|---|---|---|
| 1 | карма | `karma > 0` — имя тянется в красный |
| 2 | флаг | `guiltyStatus == 1` — фиолетовый |
| 3 | **сервер**, `nameColor` | значение пришло в `NpcInfo` с тегом `0xC0` |
| 4 | **`npcname-e.dat`** | цвет титула не из списка нейтральных |
| 5 | сток | градиент по разнице уровней, на практике белый |

Титул — тем же `nameColor`, и решается это не при отрисовке, а при разборе
пакета:

| приоритет | откуда | когда срабатывает |
|---|---|---|
| 1 | **сервер**, `nameColor` | значение пришло в `NpcInfo` с тегом `0xC0` |
| 2 | **`npcname-e.dat`** | всегда — обработчик пишет его первым |

У титула нет ни нейтральных цветов, ни исключений: врезка смотрит только на тег.
`FFFFFF` с сервера покрасит титул в белый — а имя того же NPC не покрасит, см.
оговорку выше.

Отсюда же ответ, зачем оба патча: серверный цвет задаётся на каждого NPC
отдельно и меняется в рантайме, дат-овский — на весь id сразу и не требует ни
строчки на сервере.

## 9. Имена и титулы с сервера

`ServerSideNpcName` и `ServerSideNpcTitle` в `config/npcs/npcs.properties`
(обе включены) заставляют сервер слать имя и титул **каждого** NPC, а не только
тех, у кого в XML стоит `usingServerSideName` / `usingServerSideTitle` —
поштучные свойства продолжают работать поверх.

`data/xml/npcs` становится единственным местом, где эти строки живут:
переименование NPC больше не требует правки клиента. Обратная сторона — игроки
видят ровно то, что написано в XML, и на локализованном клиенте это заменит
локализованные имена на датапаковые.

**Цвет титула это не затрагивает.** Он не строка и приезжает своим каналом —
`nameColor` с сервера, а если его нет, то `npcname-e.dat` по id NPC. Красится то,
что приехало текстом, чем бы оно ни было.

Так и написан [npc_level_titles.ps1](../tools/datapack/npc_level_titles.ps1): он
кладёт в `title` уровень монстра, а в `nameColor` — цвет по виду монстра. См.
[npc-level-titles.md](npc-level-titles.md).

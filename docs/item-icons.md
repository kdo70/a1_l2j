# Иконки предметов на сервере

Interlude хранит иконку предмета только на клиенте — в `weapongrp.dat`, `armorgrp.dat` и
`etcitemgrp.dat`. По id предмета сервер её не знает и в HTML нарисовать не может: тег
`<img src="icon.etc_adena_i00">` требует готовое имя текстуры.

Поэтому таблица клиента один раз выгружена в датапак — `data/xml/itemIcons.xml`. Её читает
`ItemIconData` (`net.sf.l2j.gameserver.data.xml`), и любой генерируемый HTML может нарисовать
предмет. Сейчас этим пользуется окно дроп-листа — [droplist-window.md](droplist-window.md).

Соседние фичи того же рода: навыки и цвет названия предмета — [item-skills.md](item-skills.md),
характеристики с сервера — [item-stats-from-server.md](item-stats-from-server.md).

---

## 1. Файл

```xml
<list default="noimage">
	<item id="57" icon="etc_adena_i00" />
	...
</list>
```

`icon` — голое имя текстуры, пакет `icon.` сервер подставляет сам. Предмет, которого в списке нет,
рисуется иконкой из `default` (`icon.noimage`), так что пропуск не ломает вёрстку страницы.

Покрытие текущей выгрузки — 9192 предмета из 9208, что есть в `data/xml/items`. Недостающие 16
(id 709–724, старые дубликаты кожаных доспехов) в `armorgrp.dat` клиента просто отсутствуют.

Перечитать на живом сервере — `//reload drop` (вместе с `droplist` и `droplist.xml`).

## 2. Как выгрузить заново

Нужно, если в клиент добавили предметы.

Шаг 1 — расшифровать три таблицы. Клиент отдаёт их с заголовком `Lineage2Ver41x`; любой
`l2encdec` их разбирает (`-l` для ретейльных ключей, `-d` для «новых» RSA-пар, которыми пожаты
сборки большинства пиратских клиентов):

```
l2encdec.exe -d <client>\system\etcitemgrp.dat  <куда>\etcitemgrp.dat
l2encdec.exe -d <client>\system\weapongrp.dat   <куда>\weapongrp.dat
l2encdec.exe -d <client>\system\armorgrp.dat    <куда>\armorgrp.dat
```

Шаг 2 — собрать XML. Скрипт пишет сразу в оба дерева датапака (`source/aCis_datapack` и `build/`):

```powershell
powershell -ExecutionPolicy Bypass -File tools\icons\grp_to_icons.ps1 -GrpDir <куда>
```

Он печатает, сколько записей нашёл в каждой таблице и сколько предметов датапака сматчил. Если
число сматченных заметно упало — что-то поехало, коммитить результат не надо.

## 3. Как это разбирается

Схемы записи у `*grp.dat` нет: внутри переменной длины массивы мешей и текстур, и по полям её
разобрать без описания формата нельзя. Скрипт опирается на две вещи, которые опознаются сами:

* заголовок записи — `tag` (0 оружие, 1 доспех, 2 etcitem) и сразу за ним id предмета;
* строку `icon.<имя>` с префиксом длины, которую запись обязательно несёт.

Мусорные последовательности байт тоже похожи на заголовок, поэтому настоящие отбираются по трём
признакам: id есть в `data/xml/items`, следом за ним идут пять маленьких счётчиков (внутри
UTF-16-строки на их месте были бы огромные числа), и id по файлу только растут — записи
отсортированы. Из кандидатов берётся самая длинная возрастающая цепочка, и каждой записи достаётся
первая иконка, написанная после неё.

Щиты датапак считает доспехами, а клиент держит их в `weapongrp.dat`, поэтому они читаются
отдельным проходом.

Проверка простая и её стоит делать после каждой перевыгрузки: id 1 — `weapon_small_sword_i00`,
57 — `etc_adena_i00`, 736 — `etc_scroll_of_return_i00`. Если хотя бы один сдвинут на соседний
предмет, цепочка порвалась и весь файл врёт.

# Заточка с повтором и модификация клиента

Знания, добытые при реализации «окно заточки не закрывается + кнопка Повтор».
Большая часть — про клиент Interlude, потому что серверная половина оказалась
тривиальной, а вся сложность лежала на стороне клиента.

Дополняет [AGENTS.md](../AGENTS.md). Инструменты и пошаговая инструкция по
пересборке клиента — в [tools/client/README.md](../tools/client/README.md).

---

## 1. Что сделано

**Сервер.** Конфиг `EnchantKeepWindowOpened` в `config/players.properties`
(по умолчанию `False`, читается только при старте). Когда включён, после
удачной попытки сервер не закрывает окно заточки, а отдаёт клиенту следующий
свиток того же id — если вещь уцелела, ещё точится этим свитком и свиток есть
в инвентаре. Любой из этих отказов = окно закрывается штатно.

**Клиент.** Пересобранный `interface.u` (класс `ItemEnchantWnd`) и
`interface.xdat` с третьей кнопкой:

| кнопка | id подписи | поведение |
|---|---|---|
| `btnOK` | 140 | точит выделенный предмет, окно закрывается |
| `btnRepeat` | 1501 | точит запомненный предмет, окно остаётся |
| `btnCancel` | 141 | отмена |

Изменённые файлы сервера:
`Config.java`, `RequestEnchantItem.java`, оба `players.properties`.

## 2. Форматы клиента

### Контейнер `Lineage2Ver111`

`interface.u`, `nwindow.u`, `uwindow.u`, `core.u`, `engine.u` и прочие `.u`:

```
[28 байт]  "Lineage2Ver111" в UTF-16
[тело]     Unreal-пакет, каждый байт XOR 0xAC
[20 байт]  хвост открытым текстом
```

Хвост недокументирован — при перепаковке копируется из стокового файла, а не
выдумывается. XOR — сам себе обратная операция, поэтому патчить можно прямо в
зашифрованных байтах: `raw = value XOR 0xAC`.

### Unreal-пакет

Версия **123**, licensee **30**. Обычный UE2-формат: таблицы имён, импортов,
экспортов; индексы объектов и имён хранятся compact-индексами (1–5 байт).

Важное: **раскладка `UFunction` одинакова при licensee 0 и 30** — проверено
побайтово на `Core.u` кита (lic 0) и `interface.u` клиента (lic 30). Поэтому
пакет, собранный ucc с licensee 0, совместим; при упаковке поле licensee
переставляется в 30, чтобы файл выглядел как остальные.

### `interface.xdat`

**Не зашифрован.** Плоский последовательный поток без абсолютных смещений,
поэтому вставка контрола безопасна. Строки — с однобайтовой длиной,
включающей терминатор.

Схема из XDAT Editor, которая читает Interlude-файл, — **`ct0`**, не `ct1`
(`ct1` падает с EOF). В `ct0` позиция контрола — это `anchor_x`/`anchor_y`
(целые), размер — `size_absolute_width/height`, подпись кнопки —
`buttonName` (id системной строки).

### `sysstring-e.dat`

`Lineage2Ver413` — RSA. Ключом, зашитым в `l2crypt` из XDAT Editor, **не
расшифровывается**: перебраны все 6 модулей на экспонентах `1d/25/35/11`,
совпадений нет. Строку 1501 владелец сервера добавил сам сторонним
редактором (**L2 File Editor by CriticalError**,
`C:\Users\KRIVOSHEEC\Desktop\L2_File_Editor_2a__C4_to_Freya__by_CriticalError`).

## 3. Ловушки, стоившие дороже всего

### `defaultproperties` нет в `ScriptText`

`ScriptText` внутри пакета содержит **только код класса**. Ни один из 142
классов не несёт блока `defaultproperties`. Пересборка «как есть» обнуляет
все значения по умолчанию, и клиент разваливается: нет экрана загрузки,
пустой инвентарь, мёртвый статус, подвисания раз в несколько секунд.
Выглядит как мусор от компилятора — но код при этом побайтово верный.

Значения лежат в хвосте каждого `UClass`-экспорта тегированным списком
свойств. Их достаёт `tools/client/extract_defaults.ps1` и дописывает в
исходники (36 классов). **Запускать обязательно** после извлечения исходников.

### Критерий проверки без запуска игры

Самая надёжная офлайн-проверка — **сравнение размеров всех `UClass`-экспортов
со стоковым пакетом**. Верная пересборка отличается ровно одним классом — тем,
который правили. Именно эта проверка ловит потерянные дефолты; проверка
импортов и байткода её не ловит, потому что дефолты лежат в другом месте.

Расхождения по ±1–3 байта в функциях посторонних классов — норма: ссылки
кодируются compact-индексами, а таблица имён у пересобранного пакета
упорядочена иначе.

### `SetItem` уничтожает выделение

`ItemWindowHandle` умеет `ClearSelect`, `GetSelectedNum`, `GetSelectedItem` —
**сеттера выделения нет**, и в структуре `ItemInfo` (60 полей) поля выбора
тоже нет. Замена записи через `SetItem` сбрасывает выбор безвозвратно.

Отсюда жёсткий размен: либо обновляем запись и уровень заточки верный, либо
не трогаем и выделение живёт. Развязывается только отдельной кнопкой, которая
работает по запомненному `ServerID` и в выделении не нуждается.

### `InventoryUpdate` уходит тиком 333 мс

`setEnchantLevel` не шлёт пакет, а ставит предмет в очередь; рассылает
`InventoryUpdateTaskManager` раз в 333 мс. Сервер же отправляет
`ChooseInventoryItem` немедленно, и клиент строит список из ещё не
обновлённого инвентаря — отсюда «уровень отстаёт на 1», причём плавающе, по
гонке. Лечится `player.sendIU()` перед `ChooseInventoryItem`;
`AbstractInventoryUpdate.writeImpl` в конце делает `_items.clear()`, так что
дубля от таск-менеджера не будет.

### Кнопки неразличимы для сервера

`btnOK` и `btnRepeat` шлют **один и тот же** пакет
`RequestEnchantItem(objectId)`. Различить их сервер не может в принципе —
решение о закрытии окна принимает только клиент. Клиент же, закрывая окно
после `OK`, возвращает серверу отложенный свиток через
`RequestEnchantItem(-1)`; чтобы это не сыпало «Enchant scroll cancelled» после
каждой заточки, сервер при включённом конфиге делает такую отмену молча.

### Мелочи, на которых легко потерять время

- `ucc` и dll кита 32-битные и требуют **Visual C++ 2013 x86** (`msvcr120.dll`).
  Без него — выход `0xC0000135` и ни строчки вывода.
- Скрипты неподписанные: запускать `powershell -ExecutionPolicy Bypass -File ...`.
- `copy /Y` — это cmd; в PowerShell нужен `Copy-Item ... -Force`.
- В PowerShell `$out` и `$Out` — одна переменная (регистр не различается).

## 4. Пересборка клиента

Кит компилятора: `C:\Users\KRIVOSHEEC\Desktop\L2Editor`. Что важно — он
**L2-совместимый**: в `UCC.exe` есть `Lineage2111WindowsFileReader`, в
`Engine.dll` — `LineagePlayerController`. Проверять любой новый кит так же.

Собирает [tools/client/build_interface.ps1](../tools/client/build_interface.ps1)
одной командой. Обходные пути, которые он делает и без которых не собирается:

- **Пакеты берутся из кита, не из клиента.** `Core.dll` кита вяжется только со
  своими пакетами; клиентский `core.u` даёт
  `Can't find 'intUObjectexecRotator2Vector' in 'Core.dll'`.
- **`Core` пересобирается** из исходников кита плюс `ParamStack` из клиента
  (в `Core` кита его нет, а Interlude-интерфейсу он нужен). Это и даёт в
  результате правильный импорт `Core.ParamStack`. Из подменного `Object`
  убран `Split`: в клиентском `Object` его нет, а `UICommonAPI` объявляет
  свой, и ucc иначе ругается `specifiers differ from original`.
- **`NWindow` пересобирается со снятым `native`**: движок кита падает на
  бинарном `nwindow.u` клиента, а клиентский `nwindow.dll` в процесс кита не
  грузится. Ненумерованные нативы компилируются в те же опкоды, а от NWindow
  нужны только имена и сигнатуры — собранный `NWindow.u` выбрасывается.
- **`dynamicrecompile` и `constructive`** — модификаторы более поздней
  хроники, этот ucc их не знает, вырезаются из исходников.

Кнопку в `interface.xdat` добавляет
[tools/client/add_repeat_button.groovy](../tools/client/add_repeat_button.groovy)
на библиотеках XDAT Editor (`C:\Users\KRIVOSHEEC\Desktop\xdatEditor`). Допуск
к работе — round-trip: чтение и запись без изменений дают байт-в-байт тот же
файл.

Бэкапы стока лежат рядом с клиентом:
`system\interface.u.orig.bak`, `system\interface.xdat.orig.bak`.

## 5. Названия и цвета предметов (разведка)

Цвет названия по итогам этой разведки сделан — см. [item-name-colors.md](item-name-colors.md).
Ниже сама разведка, она объясняет, почему сделано именно так.

Названия сейчас целиком клиентские: `itemname-e.dat` + `UIDATA_ITEM.GetItemName(id)`.
В протоколе строки названия нет — `InventoryUpdate`/`ItemList` чисто числовые,
а `SystemMessage` шлёт id (`TYPE_ITEM_NAME = 3`).

Что при этом доступно:

- **Уже сейчас, без правки клиента.** `addString(text)` (`TYPE_TEXT = 0`)
  кладёт в системное сообщение строку с сервера. HTML-окна (диалоги NPC,
  комьюнити-борд) — текст и `<font color=...>` целиком серверные.
- **Правкой `interface.u`.** Название в окнах предметов задаёт скрипт, а не
  движок: стоковые `ActionWnd`, `MultiSellWnd`, `RecipeShopWnd` и другие сами
  пишут `infItem.Name = ...`. `InventoryWnd.HandleAddItem` просто не
  переопределяет пришедшее из `ParamToItemInfo`, но может.
- **Полностью серверные имена** требуют самодельного транспорта: подходящие
  каналы до скрипта — `EV_ChatMessage` (`ParseString(param, "Msg", text)`) и
  `EV_SystemMessage`.

Про цвет:

- **Тултипы — да, полностью.** `ToolTip.uc` собирает подсказку поэлементно и
  красит каждый элемент (`m_Info.t_color.R/G/B/A`).
- **HTML — да, уже сегодня.**
- **Сетка предметов — нет.** Поля цвета в `ItemInfo` не существует, имя
  рисуется простым текстом. Практичный обходной путь — `IconName` и
  `ForeTexture` (цветная рамка/подложка вместо цветных букв).

Реализовано по этому пути: цвет из xml датапака едет на клиент фидом по
`EV_ChatMessage`, `ToolTip` красит им имя предмета. Подробности —
[item-name-colors.md](item-name-colors.md).

## 6. Что не проверено

- Пересобранный `interface.u` (уже вместе с правками из
  [item-name-colors.md](item-name-colors.md)) поставлен в клиент, клиент
  запускается и интерфейс работает. Поведение самих правок заточки — уровень в
  окне, уровень в сообщении, закрытие по `OK`, не-закрытие по `Повтор` —
  точечно не перепроверялось.
- Пересобраны все 142 класса интерфейса компилятором из другой хроники.
  Импорты и размеры блоков классов сходятся со стоком, но поведение всех
  посторонних окон целиком не проверялось.
- Серверный jar собирается деплоем (CI на push в `main`), локально не
  собирается — его временная метка в `build/` не показатель актуальности.

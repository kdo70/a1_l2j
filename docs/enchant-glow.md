# Свечение заточенного оружия

Свечение растёт вместе с заточкой: у каждого вида оружия семь ступеней — **+4, +7, +10, +12, +14,
+15, +17**. Эффекты лежат в `EnchantGlow.u` (кладётся в `system\` клиента), выбирает их
пропатченный `engine.dll`, а какой именно вид оружия перед ним — он узнаёт из `weapongrp.dat`.

Правка целиком клиентская: сервер про свечение не знает ничего. Соседние клиентские фичи и форматы —
[enchant-and-client-modding.md](enchant-and-client-modding.md), лестница грейдов, на данных которой
этот патч едет, — [weapon-grades.md](weapon-grades.md).

---

## 1. Как было

Стоковый Interlude умеет ровно две вещи, и обе описаны в секции `[EnchantEffect]` файла
`system\env.int`:

```
EnchantMeshShow=4        с этой заточки вокруг оружия рисуется МЕШ (EnchantedMesh из weapongrp,
                         в ретейле это LineageWeapons.rangesample)
EnchantEffectShow=7      с этой заточки спавнится ЭФФЕКТ (EnchantedEffect из weapongrp)

Enchant0=(R1=...,G1=...,B1=...,Opacity=...,Num=...)
Enchant1=...             цвет и плотность меша, по одной строке на уровень заточки
```

`EnchantedEffect` — **одно имя на предмет**, и в стоке оно заполнено только у 242 предметов A и S
грейда (`LineageEffect.c_u000`..`c_u008`). То есть светилось только топовое оружие, всегда одинаково,
начиная с +7.

Устройство читается прямо из `engine.dll`: `FL2GameData::WeaponItemDataLoad` разбирает у оружия поля
`EnchantedEffect`, `EnchantedEffectOffset/Scale/Velocity`, `EnchantedMesh`, `EnchantedMeshOffset/Scale`
(в ddf L2 File Editor они названы `effA`/`effB`, `junk1A/B`, `rangeA/B`, `junk2A/B`), а
`APawn::GetEnchantedWeaponEffect` отдаёт первое из них вызывающему.

## 2. Как стало

`EnchantGlow.u` (339 экспортов, 56 классов-эффектов) даёт по семь ступеней на восемь видов оружия:

```
EnchantGlow.enchant<уровень>_<вид>t
             4 7 10 12 14 15 17
```

| вид | что это | какие классы датапака |
|---|---|---|
| `_001t` | кулачное | `DUALFIST` |
| `_002t` | кинжал и древковое | `DAGGER_P`, `DAGGER_M`, `POLE` |
| `_004t` | меч | `SWORD_P`, `BIGSWORD` |
| `_005t` | посох и двуручная дубина | `BIGBLUNT_P`, `BIGBLUNT_M` |
| `_006t` | парные мечи | `DUAL` |
| `_007t` | одноручная дубина и мистическое | `BLUNT_P`, `BLUNT_M`, `SWORD_M`, `ETC_M` |
| `_008t` | лук | `BOW` |
| `_010t` | рапира | в Interlude нет, ступени собираются, но никем не используются |

`EnchantGlow.enchant10_004t` — анимация +10 для мечей.

Обе половины ставятся двумя скриптами:

| скрипт | что делает |
|---|---|
| `tools/weapons/patch_client.ps1` | пишет в `weapongrp.dat` каждому оружию лестницы **+4-эффект его вида** (`EnchantGlow.enchant4_004t` мечу, `_008t` луку и так далее), в `effA`, а у двухмешевого оружия ещё и в `effB` |
| `tools/client/patch_engine_enchant_glow.ps1` | патчит `engine.dll`, чтобы это имя поднималось по ступеням вместе с заточкой |
| `tools/client/patch_env_enchant.ps1` | ставит `EnchantEffectShow=4`, иначе клиент не спросит эффект раньше +7 |

Порядок правил такой:

```
эффект оружия — не один из восьми   -> отдаётся как есть (чужие и стоковые эффекты не трогаются)
заточка меньше +4                   -> NAME_None, свечения нет вообще
+4..+6  +7..+9  +10..+11  +12..+13  +14  +15..+16  +17 и выше   -> эффект своей ступени
```

Из этого следует, что **половинки независимы**: стоковый `weapongrp` через патченный движок проходит
без изменений, а патченный `weapongrp` на стоковом движке просто светится +4-эффектом с +4 и выше.

Меш (`EnchantMeshShow`, ретейльная «аура» с цветами из `Enchant0..N`) не тронут: он рисуется как
рисовался, с +4. Отключается вручную — `patch_env_enchant.ps1 -MeshShow <уровень>` (только на
значение той же ширины, скрипт правит цифру на месте).

## 3. Патч движка

`APawn::GetEnchantedWeaponEffect(FName&, FVector&, float&, float&, int)`, файловое смещение
`0x32B770` (RVA `0x32C370`, за инкрементальным thunk'ом `0x69AB`). Пролог из пяти байт
(`push ebp / mov ebp,esp / push -1`) заменён на `jmp` в пещеру.

**Пещера** — `0xCC`-набивка сразу за таблицей thunk'ов инкрементального линковщика, файловое
смещение `0x14A00` (RVA `0x15600`); её там 65543 байта, туда никто не прыгает. Занято 4352 байта:

| смещение в пещере | что |
|---|---|
| `+0x0000` | обёртка |
| `+0x0180` | трамплин: вытесненный пролог и прыжок в тело функции |
| `+0x0190` | флаг «таблица построена» |
| `+0x01A0` | 56 индексов `FName` |
| `+0x0300` | 56 имён, UTF-16, по 64 байта на слот |

Обёртка перекладывает пять аргументов и `this`, зовёт оригинал через трамплин, а потом переписывает
`FName`, который тот положил, и возвращает тот же указатель. Имена строятся один раз, при первом
вызове, через импорт `core.dll` — `FName::FName(const TCHAR*, EFindName)` c `FNAME_Add`, — и остаются
в пещере.

Уровень заточки берётся из `APawn::AttackItemEnchantedValue`, поле `+0x1830`: это ровно то, что
вызывающая функция сравнивает с `EnchantEffectShow`, прежде чем вообще спросить эффект.

**Абсолютных адресов в пещере нет.** Она узнаёт, куда её загрузили, из `call`/`pop` и через эту
разницу достаёт и свою таблицу, и свои строки, и импорт — поэтому записи в `.reloc` не нужны, ровно
как в [npc-name-colors.md](npc-name-colors.md).

Скрипт сверяет пролог функции побайтово и проверяет, что вся пещера — `0xCC`, так что на другой сборке
он просто откажется работать. Стоковый файл остаётся рядом как `engine.dll.enchantglow.bak`; повторный
прогон по уже пропатченному файлу упрётся в проверку пещеры — откатывайтесь бэкапом.

### Что осталось непроверенным

- **Обновление на лету.** Вызывающая функция кеширует построенный эффект по id оружия
  (`[pawn+0x182C]` против `[pawn+0x6A0]`), а не по уровню заточки. Переход, скажем, с +9 на +10 может
  не перерисоваться, пока оружие не переоденут или пока игрок не перезайдёт. Проверять живьём.
- **Загрузка пакета.** Имя `EnchantGlow.enchant4_004t` резолвится тем же путём, что стоковое
  `LineageEffect.c_u007`; предполагается, что клиент подтянет `EnchantGlow.u` из `system\` сам.
- Сами 56 эффектов не просмотрены — какого они цвета и размера, видно только в игре.

## 4. Изменённые файлы клиента

| файл | чем | бэкап |
|---|---|---|
| `system\weapongrp.dat` | `tools/weapons/patch_client.ps1` | `weapongrp.dat.weapons.bak` |
| `system\itemname-e.dat` | `tools/weapons/patch_client.ps1` | `itemname-e.dat.weapons.bak` |
| `system\engine.dll` | `tools/client/patch_engine_enchant_glow.ps1` | `engine.dll.enchantglow.bak` |
| `system\env.int` | `tools/client/patch_env_enchant.ps1` | `env.int.enchantglow.bak` |
| `system\EnchantGlow.u` | кладётся руками, ничем не правится | — |

Пересборка `interface.u` тут ни при чём, `ClientVersion` эти файлы не сторожит: игрок без них просто
увидит старое свечение (или ошибку об отсутствующем пакете, если `weapongrp` у него новый, а
`EnchantGlow.u` нет, — раздавать их надо вместе).

# Спавн-лист в базе данных

Весь спавн NPC переехал из `data/xml/spawnlist/*.xml` в таблицы `spawnlist_*`. Каталога `spawnlist` в
датапаке больше нет — его просто нет, и `SpawnManager` про него не знает. Править спавн теперь можно на
живом сервере одним `UPDATE` плюс `//reload spawn`, без пересборки датапака и без рестарта.

Сюда же попал и **ручной спавн GM-а**: то, что заспавнено командой `//spawn`, ложится в таблицу
`spawnlist_custom` и переживает рестарт (раздел 5).

Соседняя фича того же рода — дроп в БД, [droplist-in-db.md](droplist-in-db.md).

---

## 1. Таблицы

Схема и все ретейльные данные лежат в `sql/spawnlist.sql` (~6,5 МБ, 9432 территории, 10 072 npcmaker'а,
30 137 строк спавна). Ручной спавн — отдельный файл `sql/spawnlist_custom.sql`, он только создаёт пустую
таблицу.

XML описывал спавн двумя уровнями — территория (многоугольник, внутри которого NPC ходят и возрождаются)
и npcmaker (группа спавна, привязанная к территории). Ровно это и разложено по шести таблицам:

| таблица | что в ней | ключ |
|---|---|---|
| `spawnlist_territories` | имя территории и её пределы по Z | `name` |
| `spawnlist_territory_nodes` | вершины многоугольника **по порядку обхода** | `(territory, order_id)` |
| `spawnlist_makers` | группа спавна: территория, лимит NPC, тип maker-скрипта, событие | `name` |
| `spawnlist_maker_params` | AI-параметры maker-скрипта | `(maker, name)` |
| `spawnlist_npcs` | строка спавна: какой NPC, сколько, где, с каким респауном | `(maker, order_id)` |
| `spawnlist_npc_params` | AI-параметры строки спавна (`flee_x`, `MoveAroundDistance`, ...) | `(maker, npc_order, name)` |
| `spawnlist_npc_privates` | минионы строки спавна | `(maker, npc_order, order_id)` |

Связь везде по имени: строки спавна ссылаются на `spawnlist_makers.name`, параметры и привэйты — на пару
`(maker, npc_order)`, то есть на `spawnlist_npcs.(maker, order_id)`. Внешних ключей нет намеренно —
`spawnlist.sql` сносит и заливает таблицы в один проход, а порядок заливки при FK стал бы жёстким.

### spawnlist_territories / spawnlist_territory_nodes

`order_id` в нодах — **не украшение**: это порядок обхода многоугольника, по нему считается триангуляция
(`Kong.doTriangulation`). Переставите вершины местами — получите другую фигуру или ошибку триангуляции в
логе. Меньше трёх вершин — территории не будет.

`min_z` / `max_z` ограничивают территорию по высоте: NPC, вышедший за эти пределы, считается вне своей
территории.

### spawnlist_makers

| колонка | что |
|---|---|
| `territory` | имя территории; **несколько имён через `;`** объединяются в одну составную территорию |
| `ban_territory` | территория-вырезка: внутри неё спавн запрещён, формат тот же |
| `maximum_npcs` | сколько NPC группа держит одновременно; домножается на `SpawnMultiplier` из конфигов |
| `maker_type` | какой maker-скрипт рулит группой (`default_maker`, `random_spawn`, `on_day_night_spawn`, ...); незнакомое значение молча даёт `default_maker` |
| `event` | имя события; группа с событием **не спавнится на старте**, её поднимает `SpawnEvents` из конфига или сам сервер (Seven Signs) |
| `spawn_time` | привязка к осадному/агитному таймеру, формат `имя(параметры;через;точку с запятой)` |
| `enabled` | `0` выключает всю группу, не удаляя её |

### spawnlist_npcs

| колонка | что |
|---|---|
| `npc_id` | id NPC из `data/xml/npcs` |
| `total` | сколько экземпляров держать; при заданном `db_name` игнорируется — такой NPC всегда один |
| `respawn` / `respawn_rand` | **секунды**; `respawn_rand` это разброс `±` вокруг `respawn` |
| `pos` | `X;Y;Z;heading` — фиксированная точка; `X;Y;Z;heading;шанс` повторённое N раз — случайная из списка; `NULL` — случайная точка территории |
| `db_name` | ключ в таблице `spawn_data`: HP/MP, координаты и время респауна такого NPC переживают рестарт (РБ, гранд-боссы) |
| `db_saving` | что именно сохраняется — ретейльное поле, сервер его сейчас не читает, хранится для полноты |
| `enabled` | `0` выключает строку, не удаляя её |

Респаун везде в секундах. `-1` — это ретейльное `respawn="no"`, `0` — респаун не задан; обе величины
сервер приводит к «не возрождается». XML-запись вида `168hour` при переносе превратилась в `604800`.

## 2. Как это читает сервер

`SpawnManager` (`net.sf.l2j.gameserver.data.manager`) при старте выбирает каждую таблицу целиком:
сначала ноды и территории (ноды группируются по имени, отсюда `ORDER BY territory, order_id`), потом
параметры/привэйты/строки спавна в индексы `Map<makerName, ...>`, и уже по ним в один проход собирает
`NpcMaker` с его `MultiSpawn`. Строка с несуществующим `npc_id` отбрасывается с предупреждением в лог —
ровно как это делал XML-парсер.

Загрузка идёт в `GameServer` после `NpcData`, сам спавн — позже, в `SpawnManager.spawn()`.

Перезагрузка на живом сервере:

```
//reload spawn
```

Это полный цикл: деспавн всех NPC, перечитывание таблиц, спавн заново — то же самое, что делает
`//respawnall`, только без перезагрузки шаблонов NPC. Половинчатого состояния не бывает, но и дешёвой
операцией это не назовёшь: перезаливается весь мир.

## 3. Как править спавн

```sql
-- выключить группу целиком, не теряя данные
UPDATE spawnlist_makers SET enabled = 0 WHERE name = 'gludio15_1621_01m1';

-- ускорить респаун конкретного NPC во всех группах: 60 сек вместо ретейльного
UPDATE spawnlist_npcs SET respawn = 60, respawn_rand = 20 WHERE npc_id = 20498;

-- посмотреть, где вообще спавнится NPC
SELECT n.*, m.territory FROM spawnlist_npcs n JOIN spawnlist_makers m ON m.name = n.maker
WHERE n.npc_id = 20498;

-- добавить NPC в существующую группу (order_id берём следующий свободный)
INSERT INTO spawnlist_npcs (maker, order_id, npc_id, total, respawn, respawn_rand)
SELECT 'gludio15_1621_01m1', MAX(order_id) + 1, 20495, 3, 60, 20 FROM spawnlist_npcs
WHERE maker = 'gludio15_1621_01m1';

-- поднять лимит группы (реальное число NPC ограничено и maximum_npcs, и суммой total)
UPDATE spawnlist_makers SET maximum_npcs = 30 WHERE name = 'gludio15_1621_01m1';
```

После правок — `//reload spawn`.

Чего делать не надо: менять `order_id` у нод территории (см. выше), задавать `total > 1` строке с
`db_name` (лишние экземпляры всё равно не появятся) и заводить группу без единой строки в
`spawnlist_npcs` — она просто ничего не заспавнит.

## 4. Установка

Свежая БД: `spawnlist.sql` и `spawnlist_custom.sql` подхватываются `tools/database_installer.bat` / `.sh`
наравне с остальными таблицами, отдельных действий не нужно.

Уже работающая БД, в которой таблиц ещё нет:

```bash
mysql -u root -p acis < build/sql/spawnlist.sql
```

```bash
mysql -u root -p acis < build/sql/spawnlist_custom.sql
```

`spawnlist.sql` начинается с `DROP TABLE` — он ставит ретейльный спавн с нуля и стирает любые ручные
правки. Это файл установки и отката к ретейлу, а не то, что гоняют регулярно. Свои правки храните
отдельным SQL-скриптом поверх него. `spawnlist_custom.sql`, наоборот, только `CREATE TABLE IF NOT
EXISTS` — его можно гонять сколько угодно, нажитый GM-ами спавн он не тронет.

Если запустить сервер, не залив таблицы, мир будет пустым: `SpawnManager` напишет в лог
`Couldn't load territories` / `Couldn't load NPC makers` и заспавнит ноль NPC.

## 5. Ручной спавн GM-а

`//spawn <id|имя> [респаун] [temp]` спавнит NPC в точке цели (или под ногами, если цели нет) и **пишет
строку в `spawnlist_custom`** — после рестарта NPC вернётся сам. Респаун по умолчанию 60 секунд.

- `//spawn 20498` — заспавнить и сохранить;
- `//spawn 20498 300` — то же, с респауном 300 секунд;
- `//spawn 20498 temp` — заспавнить **не сохраняя**, до ближайшего рестарта;
- `//delete` по такому NPC — убрать его и **удалить строку из БД**.

Сервер отвечает на `//spawn` тем, что реально произошло: `saved in database`, `until next restart` или
`couldn't be saved in database` — последнее значит, что NPC в мире есть, а в БД его нет, и рестарт его
съест.

Спавн из скриптов и квестов (тот же класс `Spawn`) в БД не попадает: сохраняется только то, что явно
попросил сохранить `//spawn`. Технически это поле `Spawn._dbId` — `0` у временных спавнов, id строки у
сохранённых.

| колонка `spawnlist_custom` | что |
|---|---|
| `npc_id` | id NPC из `data/xml/npcs` |
| `loc_x` / `loc_y` / `loc_z` | координаты; `Z` сервер уточняет по геодате при каждом спавне |
| `heading` | поворот `0..65535`; `-1` — случайный при каждом спавне |
| `respawn_delay` | секунды до возрождения; `0` — не возрождается **до рестарта** (строка-то остаётся) |
| `respawn_random` | разброс `±` к `respawn_delay` |
| `enabled` | `0` выключает строку, не удаляя её |
| `created_by` / `created_at` | кто и когда поставил спавн |

Таблицу можно наполнять и руками — это самый простой способ добавить одиночный NPC, не заводя ради него
npcmaker и территорию. Изменения подхватывает `//reload spawn`.

## 6. Инструмент

`tools/spawnlist/xml_spawns_to_sql.ps1` — тот самый конвертер, которым делали перенос. Он читает
`data/xml/spawnlist`, пишет `sql/spawnlist.sql` (в датапак и в `build/`), а с ключом `-StripXml` удаляет
каталог `spawnlist` в обоих деревьях.

```powershell
powershell -ExecutionPolicy Bypass -File tools\spawnlist\xml_spawns_to_sql.ps1
powershell -ExecutionPolicy Bypass -File tools\spawnlist\xml_spawns_to_sql.ps1 -StripXml
```

Перенос уже сделан, так что при обычном прогоне скрипт ничего не найдёт и честно об этом скажет, не
затирая SQL. Он нужен, если понадобится повторить перенос из другого набора XML — тогда
`-XmlDir <путь>` укажет, откуда брать.
